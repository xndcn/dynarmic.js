# A64 constant decoder experiment — 2026-10-23

Base: `bb7f1af`. The [named CPU cohort](../2026-10-23-named-cpu/README.md)
selected runtime A64 decode-table construction: 54.9–59.5% of compiler subtree
samples in the fixed workload and 41.3–43.0% in short CoreMark. These sample
shares motivated the experiment; they are not predicted speedups.

**Decision: not accepted.** The full-duration comparison fails the unchanged
performance budgets. The candidate implementation is retained in the evidence
archive as `source.patch`; production source remains at the `bb7f1af` behavior.
The user requested pausing the goal after this round.

## Candidate implementation and semantic evidence

The A64 adapter uses the original `a64.inc` definitions and argument decoder,
but generates the 4,096 bucket offsets and 6,113 candidate IDs at compile time.
Handlers are constant function pointers specialized on visitor methods. No
runtime table building, matcher copying or `std::function` allocation remains
in this decoder. The upstream submodule is unchanged.

ARM and A64 share `decoder_index.h`. Stable counting sort preserves specificity
ties and A64's stable partition for three priority names (four patterns: FMOV
has two forms). This avoids quadratic constexpr insertion sorting for the
larger rule set and works within Clang's default evaluation limits. The ARM
benchmark Wasm files remain byte-identical to the base implementation.

The new native test compares every ordered A64 bucket against the original
upstream runtime table, all 643 rules and bit mutations, 28 priority overlaps,
one million seeded random encodings, and 65,536 typed `Imm`/register/boolean
dispatch cases with explicit bit-field expectations. The existing ARM test
also covers zero-argument and const handlers through the shared factory.
Release and ASan/UBSan CTest pass 5/5, including 178 Node protocol tests.

Both production and profile strict regressions pass with the complete short
CoreMark workload, full differential fuzz matrix and checked-in corpus. Chrome
133 and Firefox Worker checks pass in both configurations. The production
strict run preceded registering the new native A64 test in the shell gate;
the native test passed separately and in the final profile strict run.
Adding the explicit integer-type include to the shared header and rebuilding
left all 74 checked JS/Wasm artifacts byte-identical to those runtime-tested
versions. Named diagnostic links were also rebuilt and byte-compared.

Named binary inspection shows deletion of the 67,446-byte runtime initializer.
The ordinary A64 memory host shrinks from 1,615,079 to 1,492,827 Wasm bytes.
Ten candidate named CPU runs validate and show no decode-table construction
frame. Main-module size and generated guest-module size are distinct metrics.

## Controlled short workloads

Node v24.19.0 / V8 13.6.233.17-node.51, Emscripten 6.0.13, Core i7-12700.
Affinity `0,2,4,6` selects four physical P cores; frequency is not locked.
No builds, fuzzing or browser tests launched by this session overlap these
comparisons. Baselines were rebuilt in the same build trees before wiring in
the new headers, then copied to immutable snapshots. Reports record configured
source observations, not build-time source attestations; the source patch and
artifact hashes bind the implementation under investigation.

Twenty-five fresh processes per fixed case alternate build and case order.
All existing fixed-suite budgets pass; generated byte counts are unchanged.
The A64 results below are **compile-phase sums**, not total module startup or
steady-state throughput:

| Fixed case | Before compile median (ms) | After (ms) | Warm throughput ratio |
| --- | ---: | ---: | ---: |
| A64 thunk memory | 106.226 | 40.701 | 1.019 |
| A64 page-table memory | 106.200 | 40.417 | 1.019 |
| A64 flat-window memory | 106.202 | 40.865 | 0.980 |
| A64 NEON | 83.076 | 18.003 | 0.998 |
| A64 scalar | 82.258 | 17.683 | 0.993 |

Cold compile medians fall 61–79%. Warm metrics stay within the original 5%
review budget; these small differences do not establish a warm speedup.

Population diagnostics retain an important failed comparison. The initial
25-round production comparison fails four warm-latency gates, with ratios
1.19–1.28 for sub-millisecond visits. Its baseline and candidate JS **and** Wasm
are byte-identical. The 25-round profile comparison, same-path production A/A
control and equal-length-path production A/B control all pass. This excludes a
changed executable as the cause of the original population failure; it does
not isolate path effects from engine/scheduling variability. All original
samples remain retained and no budget was widened. No population speedup is
claimed for this A64 change.

CoreMark uses 4,000 fixed iterations and six architecture/memory cases. Ten
initial alternating complete cohorts fail the A32 thunk kernel gate (ratio
1.059). A planned 25-round extension fails a different borderline case, A64
page-table kernel (1.0556). Combining **all 35 rounds**, with no discarded
samples, passes the original budgets in every case. The separate failures
remain part of the evidence.

In the combined A64 application samples, compile medians fall 41–45% and total
Run medians fall 0.5–6.7%, while kernel intervals rise 2.7–4.1%. The kernel
interval includes cold misses and engine tiering; it is not a steady-state
measurement. These short reports are not duration-qualified CoreMark scores.
The complete-duration follow-up below fails its acceptance gates; the short
combined result does not override that failure.

## Complete-duration follow-up

The separate workload fixes 120,000 iterations. `duration-paired.mjs` pairs
individual cases, rotates case order and alternates build order each round,
retains all child output, requires every guest sample to last at least ten
seconds, and verifies artifact/source/build identities before and after.
Native output is an independent CRC oracle. Five fresh processes per case and
implementation yield 60 guest executions.

```sh
python3 tests/bench/coremark/build.py /tmp/dynarmic-coremark-source \
  /tmp/dynarmic-coremark-120k --iterations 120000
taskset -c 0,2,4,6 node internals/measurements/2026-10-23-a64-decoder/duration-paired.mjs \
  /tmp/dynarmic-a64-static-evidence/baseline/examples/browser \
  build-em/examples/browser /tmp/dynarmic-coremark-120k /tmp/new-duration-cohort 5
```

All 60 executions completed, passed native/guest CRC checks and met the ten-second
requirement (observed range 13.822–64.675 seconds). Artifact, source-observation,
build and workload checks remained unchanged. The collector exited **1** for
performance failure, not a collection or correctness error.

| Case | Before kernel median ± MAD (s) | Candidate (s) | Kernel ratio | Compile ratio | Result |
| --- | ---: | ---: | ---: | ---: | --- |
| A32 thunk | 46.814 ± 5.392 | 45.801 ± 0.663 | 0.9784 | 0.6978 | PASS |
| A32 page-table | 21.003 ± 1.564 | 21.155 ± 2.226 | 1.0072 | 1.1507 | FAIL compile |
| A32 flat-window | 17.335 ± 2.381 | 17.029 ± 0.566 | 0.9824 | 1.0325 | PASS |
| A64 thunk | 43.988 ± 2.604 | 41.133 ± 2.386 | 0.9351 | 0.4507 | PASS |
| A64 page-table | 19.537 ± 0.588 | 21.283 ± 2.463 | 1.0893 | 0.6539 | FAIL kernel |
| A64 flat-window | 15.266 ± 1.444 | 17.964 ± 2.204 | 1.1768 | 0.6287 | FAIL kernel and Run |

Ratios are candidate/baseline; lower is better. MAD is median absolute
deviation, not a confidence interval. The existing kernel limit is
`1 / 0.95 = 1.05263`; compile and total Run limits are `1.15`. A64 flat-window
Run ratio is 1.1745. All emitted-byte budgets pass. Unlike the fixed suite,
the long A32 thunk emitted-byte medians differ (751,278 → 728,134); this
experiment does not establish why. A64 emitted-byte medians are unchanged.

The candidate reduces A64 compile medians by 35–55% in this long workload, but
that does not satisfy the overall performance gates. Large dispersion and the
absence of a frequency lock limit causal attribution: these results do not
prove that static decoding itself causes the slower kernel intervals. They
also do not justify dismissing the failures as noise. The 120,000-iteration
workload has different guest binary hashes from the short workload and cannot
isolate the cause of its variability. No samples were discarded, no limits
were relaxed, and no further cohort was started to seek a passing result.

The candidate was therefore removed from production source after archiving
its complete patch. This commit records a rejected experiment, not an accepted
optimization. A future explicit resume can reproduce the patch in an isolated
build and investigate engine tiering, generated code and host variability
before reconsidering it. Duration qualification is not CoreMark certification
or a performance-leadership claim.

## Retained evidence and audit

`evidence.tar.gz` contains 227 hashed files and retains the original passing
and failing comparisons, every duration child output, ten candidate CPU profiles and their validated summaries,
build/runtime logs, collection recipes, artifact hashes and `source.patch`.
The patch includes new implementation and test files relative to `bb7f1af`.
`manifest.json` records source identities; `hashes.json` covers the retained
files. SDKs, baseline executable trees and external CoreMark sources are not
vendored in this archive.

From the repository root, extract to a fresh directory and run:

```sh
mkdir /tmp/a64-decoder-evidence-audit
tar -xzf internals/measurements/2026-10-23-a64-decoder/evidence.tar.gz \
  -C /tmp/a64-decoder-evidence-audit
node internals/measurements/2026-10-23-a64-decoder/verify.mjs \
  /tmp/a64-decoder-evidence-audit
```

The audit recomputes comparisons with the existing budgets, checks that the
35-round CoreMark reports retain every original sample, validates all 60
duration child observations, and recomputes the ten CPU profile summaries.
`PASS archive audit` means evidence consistency; the individual retained
performance failures still print as failures. This does not rerun the JIT or
provide a build-time source attestation.

The archive audit passed both against the packaging directory and a fresh
extraction. The archived source patch was checked for clean application to
the retained production source. Existing local build directories still contain
the experimental candidate: reconfigure/rebuild before using them with the
restored source. No final release acceptance is implied.
