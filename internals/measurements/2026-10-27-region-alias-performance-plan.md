# A64 fallback alias performance qualification plan

Registered: 2026-10-27, before collecting alias timing samples.

## Implementations and workload

- Baseline: `f96fe7a`, with the fallback multi-entry emitter present but the
  A64 publication option disabled.
- Candidate: `6a6c6d7` backend code (the current `8ceeee5` adds only tests and
  evidence), with A64 fallback return-site aliases enabled.
- Workload: pinned CoreMark `1f483d5b8316753a742cbf5590caf5bd0a4e4777`,
  200,000 iterations, 2K performance seeds. The rebuilt workload identity is
  `ad43250ce2139ab0d0fdbf1eac0bb1284e00fde62419d387accfe6348cca17aa`;
  A64 and native executable hashes exactly match the retained static-gate
  workload.
- Both implementations use independent Release, profile-OFF Emscripten builds.
  No generated-code execution counters or dumping are enabled.

## Replacement mechanism gate

The earlier exact `111 - 16 = 95` prediction remains a failed gate and is not
rewritten. It incorrectly treated baseline Boolean coverage as a closed
prediction of candidate compilation history. This new experiment uses a forward
publication model instead of subtracting baseline coverage.

Before any timing collection, the retained candidate diagnostic history must
satisfy all of these rules under `alias_replay.mjs`:

1. Starting from an empty cache, process actual candidate misses in order.
2. Publish only the original entry and emitted, non-entry return sites of an
   A64 non-single-step fallback region. Never overwrite a live descriptor.
3. Require every original miss to be unpublished, every earlier generation to
   remain live, and no invalidation. An original compiled while its alias is
   live is a hard failure.
4. Require the independently categorized history to contain no alias-reused
   entry outside the original coverage set. Owner-absorption dependencies,
   ordinary interior-block absorption and newly exposed original entries are
   explicit outcomes, not errors and not inputs to an expected region count.
5. Require normal guest termination, native/guest CRC equality and no more than
   10% generated-byte growth.

This mechanism gate does not require 99 regions and does not infer dynamic
hotness from static reuse. The frozen analysis already satisfies rules 1–5:
publication replay reports 26 aliases, nine conflicting exposures and zero
live-original conflicts; generated bytes decrease by 18.66%. This authorizes a
new timing experiment; it does not retroactively pass the earlier 95-region
experiment or establish a speedup.

## Timing protocol and acceptance

1. Run a five-round short paired six-case screen, rotating cases and alternating
   implementation order. This is a smoke/diagnostic screen only.
2. If correctness and mechanism checks hold, run five fresh processes per
   implementation for every A32/A64 × memory-mode case at 200,000 iterations,
   again alternating implementation order and rotating cases. Every guest
   sample must meet ten seconds. Use affinity `0,2,4,6`, empty `NODE_OPTIONS`,
   no concurrent builds/tests, and retain all observations and failures.
3. Apply the unchanged CoreMark comparator: at most 5% kernel-throughput loss,
   15% Run/compile-latency growth and 10% emitted-byte growth. Inspect MAD and
   raw samples; no sample exclusion or budget widening is allowed.
4. Accept the alias implementation only with correct execution and passing
   performance gates. A throughput-neutral result may be justified by reduced
   generated bytes, but is not called a speedup. A failed result requires
   disabling/redesigning the feature or a separately explained noise follow-up;
   the original failure remains evidence.

After qualification, use fresh Run-scoped profiles of the accepted implementation
to select the next runtime optimization. Do not broaden aliases to structured
regions or resume global region-cap sweeps.
