02 / Node.jsThree ARM instructions. One answer.

Save as hello.mjs, then run node hello.mjs. svc returns control to your JavaScript host; it does not call an operating system.

hello.mjs / ARM32
import {createEmulator} from 'dynarmic.js';

const cpu = await createEmulator({
  architecture: 'a32', memorySize: 65536,
});
try {
  // mov r0, #40; add r0, r0, #2; svc #7
  cpu.writeMemory(0x1000, Uint8Array.of(
    0x28, 0x00, 0xa0, 0xe3,
    0x02, 0x00, 0x80, 0xe2,
    0x07, 0x00, 0x00, 0xef,
  ));
  cpu.setPC(0x1000);
  const result = cpu.run({maxTicks: 1000});
  if (result.reason !== 'svc') {
    throw new Error(`Guest stopped: ${result.reason}`);
  }
  console.log(result.reason, result.svc, cpu.getRegister(0));
} finally {
  cpu.dispose();
}

↳ Expected output: svc 7 42

CommonJS: use await import('dynarmic.js') inside an async function. A32 register values use number; A64 uses bigint.

03 / Browser Worker + ViteAArch64 execution, off the main thread.

In a Vite application with the local package installed, add these files. Keep your existing plugins and set worker.format to 'es' in your Vite config. Load main.js from an HTML module script.

vite.config.js
export default {
  worker: {format: 'es'},
};
index.html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>dynarmic.js example</title>
<p>Open the browser console to see the guest result.</p>
<script type="module" src="./main.js"></script>
</html>
main.js
const worker = new Worker(
  new URL('./worker.js', import.meta.url),
  {type: 'module'},
);
worker.onmessage = ({data}) => {
  console.log(data); // {reason: 'svc', value: '42'}
  worker.terminate();
};
worker.onerror = (error) => {
  console.error(error.message);
  worker.terminate();
};
worker.js / AArch64
import {createEmulator} from 'dynarmic.js';
import wasmURL from 'dynarmic.js/runtime.wasm?url';

const cpu = await createEmulator({
  architecture: 'a64', memorySize: 65536,
  wasmURL: new URL(wasmURL, self.location.href),
});
try {
  // mov x0, #42; svc #0
  cpu.writeMemory(0x1000, Uint8Array.of(
    0x40, 0x05, 0x80, 0xd2,
    0x01, 0x00, 0x00, 0xd4,
  ));
  cpu.setPC(0x1000n);
  const result = cpu.run({maxTicks: 1000});
  if (result.reason !== 'svc') {
    throw new Error(`Guest stopped: ${result.reason}`);
  }
  postMessage({
    reason: result.reason,
    value: cpu.getRegister(0).toString(),
  });
} finally {
  cpu.dispose();
}

Run npx vite and open the local URL. The console should show {reason: 'svc', value: '42'}. Vite copies and fingerprints the Wasm asset through the ?url import.

For a production build, run npx vite build, then npx vite preview. Add vite/client types for TypeScript ?url imports.

Loading & lifetimeAsset URLs, budgets and cleanup.

Choose how to load. Node finds the adjacent Wasm automatically. Without a bundler, host index.js, runtime.mjs and runtime.wasm together, then import the hosted index.js from your module Worker. Serve .mjs as JavaScript and .wasm as application/wasm.

Move the asset when needed. Pass an absolute wasmURL, or supply wasmBinary as a Uint8Array or ArrayBuffer. Use one override at a time. The loading guide covers CSP and custom asset hosts.

Keep execution bounded. run() is synchronous. maxTicks is a cooperative budget checked at block boundaries, not a wall-clock deadline. Use a Worker and worker.terminate() for hard cancellation.

Release each instance. Use try/finally with cpu.dispose(). Memory reads return copies; host writes invalidate translated code. Separate factories have separate CPU state and RAM.

Need a custom C++ host?Own the memory map, callbacks and devices.

Use the C++ embedding guide for custom devices and memory callbacks. Clone the recursive source and follow the source-build Node example to build arm_jit with Emscripten, CMake and Boost headers.

How to read this comparison

The main values summarize three independent engine instances: take the median of three measured calls in each round, then the median and range of those three round medians. First-run and loading times are shown separately. Runtime order rotates, and only one observation runs at a time.

Ratios pair observations from the same round. v86 / ARM above 1 favors dynarmic.js; ARM / direct Wasm above 1 favors the direct reference. Overall ratios give each selected case equal weight. Incomplete rounds and round medians below 0.1 ms do not produce ratios. The raw samples remain in the export.

Matching the source and compiler removes some differences; instruction sets, translation, memory access and browser scheduling still differ. This measures complete execution paths. Two warmups do not prove steady-state performance. Hiding this tab immediately stops the run and invalidates its timings.

What is being measured?

Each engine runs the identical JavaScript source with identical inputs. The first pass is shown separately, followed by one unmeasured warmup and three measured repeats that reuse the engine. Charts show their median and range. All three measured samples are retained. Loading and engine initialization sit outside kernel timing; complete-call timings include different setup work, detailed with each result.

QuickJS interprets JavaScript in both builds. The ARM path also translates machine instructions into Wasm. This compares complete execution paths on your device, not isolated compiler overhead. Browser scheduling, timer precision and engine tiering affect the result; three samples are an exploration, not a performance claim. Keep this tab visible and avoid other heavy work.

LCG uses explicit unsigned 32-bit arithmetic; the sieve uses a Uint8Array; pi uses double-precision arithmetic. Every measured pass must match the fixed reference outputs. The C benchmarks above use different work counts; their times are not directly comparable.
